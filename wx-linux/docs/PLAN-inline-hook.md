# Linux 上实现「Helper 式」毫秒级消息接管 —— 技术方案

> 记录时间：2026-11-16
> 背景：当前微信群机器人靠"页面捕获"拿消息，感知延迟 1–7 秒（最差 20 秒+），
> 群里已有人反馈"反应速度慢"。本方案目标是把感知延迟压到毫秒级。

---

## 一、原理：Linux 上完全等价

Windows 上 Helper 的做法是「DLL 注入 + Detours Hook」。Linux 有一一对应的机制：

| Windows | Linux 等价物 | 我们当前状态 |
|---|---|---|
| DLL 注入 + Detours Hook | **inline hook**：`mprotect` 改代码段 + 写 `jmp`/`INT3` | 未做，能力已具备 |
| 读进程内存 | `/proc/pid/mem` | ✅ 已用（扫过 1.7GB 内存） |
| 断点调试 | `ptrace` / gdb 断点、读寄存器 | ✅ 已用（抓过 SQLCipher 密钥） |
| API 拦截 | `LD_PRELOAD` | ✅ 已用（现在就在拦截 pread/pwrite） |

结论：**"注入进程 → 劫持内部函数 → 拿消息原文"在 Linux 上完全成立。**

---

## 二、已有能力 vs 缺口

### 已验证可行
- 能往微信进程注入代码（`LD_PRELOAD=sniffer.so` 正在运行）
- 能读写进程内存（`/proc/<pid>/mem`）
- 能下断点、读寄存器（gdb 曾用于定位密钥）
- 能拿到解密后的数据页（当前机器人即靠此工作）

### 唯一缺口
在 **stripped 的静态二进制**里定位「消息处理函数」的地址。

Windows 版 Helper 有符号表和版本偏移表，所以容易；Linux 版没有符号，必须自己找。

---

## 三、定位方案（三条路径交叉验证）

### 路径 1：pwrite 调用栈回溯（已验证可行）
消息落库时在 `pwrite64` 上抓 `backtrace()`，向上爬栈：
```
pwrite64 → os_write → pagerWrite → ... → 消息处理函数
```
我们已经在 sniffer.so 里实现了 backtrace 记录（`logs/bt.log`），
之前抓到过 18 帧的调用链（偏移 0x89ea7c2 / 0x8a2b5b3 …）。

### 路径 2：perf 采样
在群里消息涌入的瞬间 `perf record -F 9999 -p <pid>`，
找用户态热点地址，与路径 1 的候选地址交叉比对。

### 路径 3：特征匹配
消息解码通常经过 protobuf 解析，可搜索特征常量/字符串引用反查调用点。

---

## 四、劫持实现（找到地址之后）

### 方案 A：INT3 + SIGTRAP（推荐，风险最低）
```
1. mprotect 目标代码页为可写
2. 保存首字节，写入 0xCC (INT3)
3. 安装 SIGTRAP 处理器
4. 命中时：从 ucontext 读寄存器 → 取参数（protobuf 缓冲指针 + 长度）
            → 解析出 发送者/内容/时间 → 写入管道
            → 单步执行（TF 标志）→ 恢复 0xCC → 继续
```
**只改 1 个字节**，出错影响面最小。

### 方案 B：inline jump（12 字节跳转）
```
movabs rax, <handler>   ; 10 字节
jmp rax                 ; 2 字节
```
需要在 trampoline 里执行被覆盖的原始指令（指令长度需感知），
实现复杂度高，暂不首选。

---

## 五、与现有系统的对接

劫持拿到消息后：
```
消息处理函数 hook
  → 提取 (发送者, 内容, 时间戳)
  → 写入命名管道 / Unix socket
  → wxbot 从管道读取（替代现在的"扫页面"）
  → 判官 / 敏感词 / LLM / 发送（全部复用现有代码）
```

**现有服务器端逻辑一行都不用改**：判官、人设、敏感词过滤、
上下文记忆、每日分析、状态面板全部保留，只是把"消息来源"换掉。

## 六、预期效果

| 环节 | 现在 | 改造后 |
|---|---|---|
| 感知 | 1–7 秒（不可控） | **毫秒级** |
| 生成 | 0.8–2 秒 | 不变 |
| 发送 | 0.5–1.5 秒 | 不变 |
| **总计** | 2.5–10 秒，抖动大 | **1–3.5 秒，稳定** |

---

## 七、风险与代价（必须接受）

| 项 | 说明 |
|---|---|
| 工作量 | 定位函数是主要成本：顺利几小时，不顺利几天 |
| 成功率 | 约 **40%**，取决于栈上能否找到干净的函数边界 |
| 稳定性 | 补丁写错会导致微信崩溃（有 systemd 守护会自动拉起） |
| 兼容性 | 微信升级后地址全变，需重新定位 |
| 合规性 | 与 Windows 版 Helper 性质相同：属于"改进程"，有风控风险 |

---

## 八、执行计划（分段验证，每步可回退）

1. **抓消息落库调用栈** —— 在 pwrite 上记录写入 `message_0.db` 时的完整栈
2. **perf 采样复核** —— 确认候选地址在消息到达时确实被调用
3. **只下断点，不改代码** —— 验证参数里能看到消息内容
4. **写 inline hook** —— 只有前三步全部通过才做，此步有崩溃风险

前三步都是**只读操作**，不会让微信崩溃；第 4 步才需要承担风险。
